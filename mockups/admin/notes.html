Design notes

What this is

A static, no-build mockup of PRD-frontend-admin.md — every screen in its §15 roadmap (A1–A7), backed by a fake CRUD API (assets/api.js + assets/routes.js) that persists to localStorage instead of a real Postgres-backed NestJS service. It exists so the PRD's hardest decisions — the §4.3 session-expiry-mid-edit flow, the §8 draft/publish model, §9's diagram-editor validation, §10's error contract — are things you can actually click through, not just read a description of, before A1–A7 get built for real in apps/web/src/app/admin/*.

The §10 error contract — live-fired

Each row below queues a real fault on the dispatcher, then fires a real request through Api.request — the same transport every screen uses — and prints exactly what came back. Nothing here is a hand-typed example.

StatusShape
422 validationsource: {"field.path": ["msg"]}, dot-paths address array rows
400 bad idsource: null — not an empty object
404source: null, contextual message rendered verbatim
409source: null, message names the conflict
429Verbatim human-readable message, never regex-parsed
501Restore button disabled+explained for unsupported entity types, never left clickable to fail
 
Click Fire to see a real response.

Two shapes that can't be demoed this way, because they're a structural property of the response rather than an error status:

  • Success, no data key at all (not data: null) — every DELETE, and GET /cv/profile when no profile exists. Enforced by arity in api.js:ok(), not by convention: ok(msg) never has a data key; ok(msg, x) always does.
  • _root key — a whole-object issue with no specific field, rendered as a form-level banner rather than attached to any input. See ui.js:applyFieldErrors.

Where this mockup can't be honest

Stated plainly rather than silently faked:

  • The httpOnly cookie + server-side gate (§3) is impossible to fake statically. The shell ships hidden and reveals itself only once Api.me() resolves — visually faithful to "no content reaches an unauthenticated visitor," security-wise not real. See the comment above mountShell in app.js.
  • TOTP accepts any 6-digit code except the literal 000000, so the wrong-code path stays reachable without a real authenticator app.
  • Media bytes are never written to localStorage — its ~5MB quota would corrupt every other row in this mockup on the first real photo. Files live as in-memory object URLs plus a metadata row; the 8 MiB cap and byte-sniffing are still real checks against the real file, they just don't survive a reload.
  • ISR propagation to the public site — there's nothing here to demonstrate; publishing in this mockup updates only this mockup's own localStorage.
  • Login credentials — any non-empty email/password succeeds except the literal password wrong (401), so the failure path is reachable without a real account.

A stated simplification

§7.1 gives each case-study section its own PUT .../sections/:kind endpoint. This mockup keeps those as four genuinely separate requests (see project-edit.html's Save handler) rather than folding them into one — it's more faithful to the real contract, not less, and it's what makes a caseStudySection revision (and its §11 501-on-restore path) something that actually happened rather than something simulated.
